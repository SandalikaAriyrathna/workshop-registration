# Design decisions

**Stack and structure.** Laravel 12, Eloquent, Blade, Breeze authentication, Alpine.js, and Vite provide a connected application with one repository and one backend server. SQLite makes local setup straightforward. Blade forms call Laravel web endpoints directly, with session authentication and CSRF protection. This avoids a second frontend application and token management within the challenge's time limit. A separately consumable JSON API is not implemented; this is an explicit trade-off against the brief's API wording.

**Permissions.** Backend role middleware applies the challenge's matrix: Admin manages accounts, Manager creates/edits workshops, and Manager/Staff view workshops/history and register/cancel attendees. Admin cannot perform workshop operations. Public signup routes are disabled. Role-aware navigation makes the permitted workflows easy to find; hidden controls are not the authorization mechanism.

**Preventing over-registration.** Registration starts a database transaction and acquires the workshop lock before checking status, time, active bookings, and capacity. Cancellation and capacity edits acquire the same workshop lock first. Capacity cannot be reduced below the current active count. On databases supporting row locks, `lockForUpdate()` serializes operations for that workshop. SQLite ignores this clause, so a no-op update acquires its writer lock before any capacity read. The lock remains held until commit/rollback, preventing two writers from accepting the same final seat based on stale counts. Transactions retry contention up to three attempts. SQLite serializes database writers, so it favors simplicity over high write throughput; heavy contention can still produce an error rather than a booking. MySQL/InnoDB is a future scaling option and should be concurrency-tested before deployment.

**History and data.** Attendees have a name and email, not an account. Cancelling changes status and records who cancelled and when; it never deletes the registration. Original registration actor/time are retained. Foreign keys restrict deletion of workshops/users referenced by history. Cancelled registrations do not consume capacity. The details screen displays both active and cancelled records.

**Assumptions.** Only future scheduled workshops accept bookings. Cancellation is permitted for any active registration, even after the workshop starts. Managers can change workshop status without automatically cancelling registrations; existing active records remain visible and count toward capacity. Dates use the configured Laravel timezone (UTC by default). Date filters include both endpoint days. The seats filter represents remaining physical capacity; users combine it with status/date filters to find bookable workshops. Repeated email addresses are allowed because the brief does not require duplicate prevention. Admins can create Manager/Staff accounts; the initial Admin is seeded.

**Validation and delivery.** Tests cover role enforcement, disabled public signup, account creation, filtering, full/closed workshops, capacity edits, cancellation freeing seats, preserved history, and repeatable seed data. A synchronized test launches four separate PHP processes against a temporary SQLite database: only one can obtain the last seat. Setup instructions include a development Admin and three future workshops. Optional waitlists, a broader audit trail, deployment, pagination, and a separate JSON API are skipped. Frontend production assets are built with Vite.
